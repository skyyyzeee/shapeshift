# 01: Каркас и `answerfile` с обходом ограничений

**What to build:** Первая сквозная нитка через движок. Пользователь пишет минимальный профиль (JSON) с включённым обходом ограничений и командой `answerfile --profile <file> --out <path>` получает файл ответов, который снимает проверки TPM, Secure Boot, ОЗУ и процессора в установщике Windows 11. Здесь же закладывается решение: модель предметной области (термины из `CONTEXT.md`), движок как консольная программа, тестовый проект, вызывающий точку входа CLI внутри процесса. Обход ограничений на этом шаге зашит в код; в каталог он переедет в 06. Сценарии спецификации: 24, 80.

**Blocked by:** None (can start immediately)

**Status:** done

## Comments

**Сделано (2026-10-19).** Решения по ходу, которых не было в спецификации:

- **Схема файла ответов — своя.** Публичной XSD от Microsoft нет, поэтому в тестах лежит схема того подмножества, которое выдаёт генератор: конверт проверяется строго, содержимое компонентов — в режиме lax. Каждый новый элемент, который начинает выдавать генератор, нужно объявлять в этой схеме. Отдельный тест проверяет, что схема ловит ошибки (неверный pass, повторяющийся Order).
- **Снимки — свой маленький помощник вместо Verify.** Свежий Verify требует объявить в сборке лицензию на спонсорство; для нескольких XML-снимков это лишнее. Эталоны: `Snapshots/<Класс>.<Тест>.verified.xml`; принять все новые снимки — прогон с `SHAPESHIFT_ACCEPT_SNAPSHOTS=1`.
- **Тесты на Microsoft.Testing.Platform** (`global.json`): .NET 10 SDK не запускает VSTest через `dotnet test`.
- **Сообщения CLI — на английском**: это лог для отчётов об ошибках; окно будет показывать свои локализованные тексты.
- **Коды выхода**: 0 — успех, 1 — сбой, 2 — неверные входные данные (профиль, файл не найден).
- **Формат профиля v1**: `formatVersion` (обязательно), `architecture` (`x64` по умолчанию; `arm64` — понятная ошибка), `bypass` (`tpm`, `secureBoot`, `ram`, `cpu`). Неизвестные поля отклоняются, чтобы опечатки не терялись молча. В 06 `bypass` переедет в твики каталога.
